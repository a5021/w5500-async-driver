# Техническое задание (Этап 1): Разработка асинхронного драйвера W5500 на чистом Си

## 1. Цель проекта
Создание оптимизированной, легковесной и переносимой библиотеки на языке **Си (C99/C11)** для управления аппаратным сетевым контроллером **WizNet W5500**. Библиотека должна поддерживать многозадачные среды (RTOS), обладать неблокирующим API, поддерживать концепцию Zero-copy при работе с DMA и легко адаптироваться под различные архитектуры микроконтроллеров (первоочередная целевая платформа — **STM32**).

---

## 2. Архитектурные требования и структура слоев

Архитектура библиотеки должна строго разделяться на три независимых уровня выполнения:

### Слой 1: Абстракция железа (HAL / Platform Interface)
*   **Изоляция платформы:** Данный слой не должен содержать логики стека TCP/IP или сокетов. Его единственная задача — управление физическими интерфейсами МК.
*   **Абстракция через коллбеки:** Вся привязка к конкретному МК реализуется через структуру указателей на функции, передаваемую при инициализации:
    ```c
    typedef struct {
        void (*spi_select)(void);
        void (*spi_deselect)(void);
        uint8_t (*spi_transfer_byte)(uint8_t byte);
        void (*spi_transfer_burst)(uint8_t* tx_buf, uint8_t* rx_buf, uint16_t len);
        void (*delay_ms)(uint32_t ms);
        void (*lock)(void);   // Опциональный хук для мьютекса RTOS
        void (*unlock)(void); // Опциональный хук для мьютекса RTOS
    } w5500_plat_if_t;
    ```

### Слой 2: Ядро протокола (W5500 Core)
*   **Чистый Си:** Код этого слоя должен быть написан на стандартном Си (C99 или C11) без использования специфичных заголовочных файлов вендоров (никаких `stm32f4xx_hal.h`, `esp_system.h` и т.д.).
*   **Многочиповость (Multi-context):** Категорически запрещено использование глобальных переменных для хранения состояния чипа. Все функции ядра обязаны принимать указатель на контекст конкретного экземпляра устройства в качестве первого аргумента:
    ```c
    w5500_result_t w5500_set_ip(w5500_handle_t handle, const uint8_t *ip);
    ```
*   **Работа с регистрами:** Прямой доступ к памяти W5500 осуществляется через макросы и перечисления, описывающие карту регистров чипа (Common Registers и Socket Registers).

### Слой 3: Прикладной асинхронный API (Socket Layer)
*   **Инкапсуляция (Opaque Pointers):** Все структуры управления сокетами и контекстом скрыты от пользователя в файлах реализации (`.c`). Пользователю доступны только непрозрачные дескрипторы (Handles):
    ```c
    typedef struct w5500_context* w5500_handle_t;
    typedef struct w5500_socket*  w5500_socket_t;
    ```
*   **Реактивная модель (Event-driven):** Основное API управления сетью должно работать на базе неблокирующих вызовов и функций обратного вызова (Callbacks) для обработки событий:
    *   `W5500_EVENT_CONNECTED` — успешное TCP-соединение.
    *   `W5500_EVENT_DATA_RECEIVED` — поступление новых данных в буфер чипа.
    *   `W5500_EVENT_DISCONNECTED` — разрыв соединения удаленной стороной.
*   Каждый коллбек должен принимать аргумент `void *user_arg` для передачи пользовательского контекста приложения.

## 3. Требования к надежности и производительности

1.  **Отказ от бесконечных циклов (No Infinite Polling):** Все внутренние операции ожидания готовности регистров чипа W5500 должны быть защищены программными таймаутами. В случае зависания шины SPI или сбоя питания чипа библиотека должна возвращать ошибку `W5500_ERR_TIMEOUT`, а не приводить к зависанию МК.
2.  **Потокобезопасность (Thread-safety):** Доступ к транзакциям SPI и критическим секциям распределения памяти сокетов внутри ядра должен защищаться с помощью функций блокировки (`lock`/`unlock`), предоставляемых RTOS через интерфейс Слоя 1.
3.  **Оптимизация передачи данных (DMA & Zero-copy):**
    *   Интерфейс Слоя 1 должен поддерживать эффективную пакетную передачу данных (`spi_transfer_burst`) для возможности задействования контроллера DMA МК.
    *   Чтение данных из приемного буфера сокета W5500 должно осуществляться напрямую в предоставленный пользователем буфер приложения, минуя промежуточные массивы драйвера.
4.  **Строгая обработка ошибок:** Все функции, выполняющие ввод-вывод или конфигурацию ресурсов, вместо `void` обязаны возвращать перечисление статуса выполнения (`w5500_result_t`).

## 4. Требования к структуре репозитория проекта

Проект должен иметь строго структурированное дерево каталогов для разделения независимых модулей:

```
├── include/              # Публичные заголовочные файлы API
│   ├── w5500.h           # Базовое API управления чипом и контекстом
│   └── w5500_sockets.h   # Событийное API сокетов
├── src/                  # Исходный код ядра библиотеки
│   ├── w5500.c           # Реализация функций ядра и работы с регистрами
│   ├── w5500_registers.h # Внутренняя карта регистров W5500 (дефайны/enum)
│   └── w5500_sockets.c   # Реализация логики управления сокетами
├── ports/                # Порты под конкретные платформы и ОС
│   ├── stm32_hal/        # Реализация интерфейса SPI/GPIO для STM32 HAL
│   │   ├── w5500_port_stm32.c
│   │   └── w5500_port_stm32.h
│   └── freertos/         # Реализация функций синхронизации (Mutex/Semaphore)
│       └── w5500_port_rtos.c
└── examples/             # Примеры использования библиотеки
    └── stm32f4_freertos/ # Демо-проект для STM32 с использованием FreeRTOS
```

## 5. Критерии приемки Этапа 1
1.  Успешная сборка ядра библиотеки компилятором GCC (с флагами `-Wall -Wextra -std=c99`) без предупреждений и ошибок.
2.  Успешное считывание регистра версии чипа `VERSIONR` (адрес `0x0039`), возвращающее константное значение `0x04` через абстрактный интерфейс Слоя 1 на тестовом стенде STM32.
3.  Корректная инициализация сетевых параметров (IP, Mac, Gateway) и конфигурация буферов памяти сокетов без использования глобальных переменных драйвера.
